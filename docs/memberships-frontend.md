# Memberships: аудит и локальный frontend-сценарий

## Что уже существовало

Конструктор с двумя типами, цена/описание/число посещений, карточки, поиск, редактирование и архивирование. Были DTO абонемента в CRM и Customer Page, один абонемент в Scanner и общий development-журнал. Назначения через UI, дат начала, заморозки/отмены и независимого использования нескольких назначений не было. Поле временного абонемента называлось периодом оплаты, хотя платежи не выполнялись.

## Что изменено

- Использованы существующие Memberships, Customers/Profile, Customer Page, Staff Scanner и Overview. Новых маршрутов и разделов нет.
- Конструктор требует целое положительное число посещений для пакета, скрывает его для временного абонемента. Период обозначает доступ (30/365 дней), а не регулярную оплату. Точные даты можно изменить при назначении.
- В профиле клиента есть назначение существующего шаблона с датами, количеством и предпросмотром условий. Назначение имеет отдельный UUID и ссылку на шаблон; условия доступа фиксируются в момент назначения.
- Компактные карточки, остаток/прогресс, даты, состояния и история используют один sessionStorage-журнал. Поддерживаются несколько назначений одного шаблона.
- Scanner списывает с выбранного назначения и показывает имя клиента, название, остаток до и после. У безлимитного абонемента есть проверка доступа, без счётчика посещений.
- Owner/Manager с `membership.create` могут назначать, замораживать, возобновлять и отменять. Использование/проверка требуют `membership.redeem`. Это только frontend UX, не серверная авторизация.
- Customer Page показывает те же назначения только существующему выбранному локальному preview-клиенту. В гостевом режиме персональных назначений нет. Фиктивная авторизация не добавлялась.
- Overview показывает компактные Active Memberships / Visits Used / Expiring Soon без выручки. Проверки безлимитного доступа не увеличивают Visits Used.
- Выбранный бизнес хранится в текущей development-сессии и сохраняется на маршрутах без `business` в URL. Новый onboarding выбирает новый бизнес.
- Все новые тексты EN/LV/RU. У select-полей единая стрелка с отступом 14px. Сравнение тарифов облегчено без изменения цен/лимитов/данных.

## Локальная модель

Состояния выводятся из календарных дат UTC, остатка и событий: Active, Scheduled, Expired, Exhausted, Frozen, Cancelled. Конечная дата включительна. Заморозка приостанавливает доступ, но не продлевает срок. Возобновление оставляет исходную дату; истёкший абонемент остаётся истёкшим. Отмена окончательна. Для истечения срока в общий журнал добавляется одно событие при следующем чтении, а не серверным заданием.

Общий журнал фиксирует назначение, использование, проверку доступа, заморозку с причиной/датой, возобновление, отмену и истечение. Операции атомарно сохраняются вместе с idempotency key; повтор запроса не списывает второй раз. Двойные клики дополнительно блокируются в UI.

Назначения/остатки/история, шаблоны, каталог и выбранный бизнес — tab-local `sessionStorage`, существующая версия журнала v1 расширена совместимыми необязательными полями. Старые записи продолжают читаться; неизвестный исходный объём старого пакета не придумывается. Повреждённые данные безопасно отклоняются. У нового назначения известен исходный объём. Личные назначения не попадают в публичный localStorage, SSR, metadata, общий кэш. Тестовые контакты вымышленные. Пароли, OTP и токены не сохраняются.

Архивированный шаблон исключён из новых назначений и действий Scanner; прежняя история остаётся доступной. Отсутствующая связанная запись не приводит к списанию.

## Граница Symfony

API-адаптеры, endpoints и backend-контракты не заменены; серверная реализация не добавлялась. Расширение событий относится к локальному frontend-представлению. В production/API-режиме локальные операции отключены. Реальное назначение, права, баланс, проверки доступа, жизненный цикл, долговременное хранение и серверная идемпотентность требуют Symfony. Покупки, регулярные платежи, автоматическое продление, синхронизация между устройствами и публичная клиентская авторизация не имитируются.

## Проверки

Результаты финальных запусков будут указаны ниже после завершения.

- Unit: назначение и даты, остаток/исчерпание, replay и конфликт ключей, freeze/resume/cancel, временной доступ, бизнес/клиент/permissions, reload/однократное истечение, несколько назначений, выбранный бизнес.
- Playwright: через UI onboarding → шаблон на 5 посещений → клиент → назначение → существующий Scanner → 4/5 → CRM/Customer Page → freeze/resume → 0/5 → блокировка → cancel → Overview → второй бизнес → переключение/reload. Отдельно безлимитный доступ и EN/LV/RU.
- Ширины: 390/430/768/1024/1440 для профиля, модального назначения, Customer Page, Scanner; Pricing дополнительно проверяется на всех пяти ширинах с axe.
- Камера/физический QR и реальные серверные операции не подтверждаются этими тестами; Scanner проверен через существующий ручной ввод preview-кода.
